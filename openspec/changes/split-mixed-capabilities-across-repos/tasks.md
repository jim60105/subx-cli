## 10. Quality Gate

- [ ] 10.1 Run `cargo fmt` and `cargo clippy -- -D warnings` and fix all warnings
- [ ] 10.2 Run `cargo nextest run --filter-expr 'test(...)' || true` and confirm the targeted modules pass
- [ ] 10.3 Run `scripts/quality_check.sh` once at the end (main agent only — do not invoke from sub-agents) and ensure it is green
- [ ] 10.4 Run `cargo test --doc --all-features` to confirm rustdoc examples still compile

**What this gate verifies for a spec-only change.** Nothing in 10.1–10.4 reads `openspec/`, so none of them can detect a defect this change could introduce. Their purpose here is inverted, exactly as in C2a: they must be green **and their output must be unchanged from the task 1.1 baseline**, which is the evidence that the change really is spec-only — that no `.rs` file, manifest, workflow, script or test was touched while 100 delta operations were applied across thirteen files in two repositories. A gate that goes red, or whose test count or warning set moves, means something outside `openspec/` was edited and the change has exceeded its scope. For 10.2, substitute a filter naming nothing this change touches (for example `cargo nextest run --workspace --filter-expr 'test(core_cli_boundary)' || true`) purely to confirm the workspace still builds and runs; there is no targeted module to exercise.

The checks that actually gate this change are in phase 8: `openspec validate --specs --strict` green at both roots with 20 and 25 capabilities, the 89-title and 58-title set equalities, the **per-capability title intersection being empty for all twelve split capabilities**, the two citation sweeps in both directions, and the fresh-clone validation. Those SHALL be treated as the gate proper, and a failure in any of them blocks the commit exactly as a red `quality_check.sh` would. The intersection check is the one that has no analogue in C2a and no analogue in any tool: it is the only thing standing between a hand-applied split and a requirement silently specified twice in two repositories.
