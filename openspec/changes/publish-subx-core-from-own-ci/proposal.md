## Why

C1 wired the two-crate release as a single `cargo publish --workspace` in `subx-cli`'s `publish-crates` job, and the specs written with it (`release-distribution`'s *Two-Crate Publication Order and Preconditions*, `crate-topology`'s *Publication stays single-pathed* clause of *The Core Repository Has Its Own CI*) normatively froze that topology: the core repository must not publish, because a second publish path could put a library version on the registry that no superproject release pins.

The premise behind that freeze — that `subx-cli` is the umbrella project for the crate pair — is wrong. `subx-core` has a second consumer, the Tauri GUI at [`jim60105/subx`](https://github.com/jim60105/subx), which depends on the core repository directly and never sees `subx-cli` at all. For that consumer the library is a first-class project with its own release cadence, and freezing publication in the CLI repository means the GUI's provider of the crate cannot cut its own release. The ownership argument inverts: a library version pinned only by a superproject release is the artifact the GUI consumer must wait for; a library version published by the library's own tag is the artifact it can depend on immediately.

The safety property C1 actually wanted — no `subx-cli` release publishes against a `subx-core` that is not on the registry at a satisfying version — does not require a shared publish job. It requires exactly one probe: the CLI's publish job asks the sparse crates.io index whether a `subx-core` version satisfies the declared caret requirement, and refuses the tag until one does. The ordering then becomes a documented precondition (tag the library first), enforced mechanically, with a legible failure instead of a late `cargo publish` dependency-resolution error.

## What Changes

**1. `subx-core` gains its own release workflow.** `subx-core/.github/workflows/release.yml`: a `v*` tag in the core repository creates the GitHub Release (notes extracted from the matching `## [VERSION]` section of `subx-core/CHANGELOG.md` by the same awk extraction the superproject uses) and publishes the crate with `cargo publish -p subx-core --token $CARGO_REGISTRY_TOKEN` (the secret already exists in this repository's Actions configuration). Preconditions mirror the superproject's discipline where it transfers to a standalone tree: clean tree, mechanical `--allow-dirty` absence guard, tag-matches-manifest assertion, already-published probe, `--dry-run` before the real upload. RC-style tags (`v*-rc.N` etc.) are marked prerelease on GitHub and skipped for publication, exactly as in the superproject. The checkout carries no `submodules:` option — the repository has none — which is precisely how the published artifact gets its provenance: the standalone tree, the same tree crates.io consumers, docs.rs and the GUI resolve.

**2. `subx-cli`'s `publish-crates` becomes single-crate.** It drops `--workspace`, the probe that selected between `--workspace` and `--workspace --exclude subx-core`, the half-published-recovery comment (there is no longer a first member whose upload can succeed before the second fails), and the Cargo ≥ 1.90 assertion — that floor was a property of `cargo publish --workspace`, and `cargo publish -p` has never required it. It keeps every guard that still has a referent: the committed-and-clean submodule assertion, the mechanical `--allow-dirty` prohibition, the hard gitlink-ancestry assertion, the tag-versus-manifest-version assertion, the already-published probe for `subx-cli` itself, and a `--dry-run` before the real upload. It **adds** the ordering precondition: probe the sparse index for a published `subx-core` version satisfying the caret requirement read from `cargo metadata` (major-equal and not below the requirement — exactly caret semantics for release versions); if none exists, fail before packaging with a message naming the remedy: tag the intended version in `jim60105/subx-core` first.

**3. The ordering contract becomes a documented, mechanically enforced two-step.** Publish `subx-core` first by tagging its repository; publish `subx-cli` second by tagging this one. The CLI job's index probe makes a violation fail early and legibly; `cargo publish` itself would fail late and obscurely, because the packaged CLI's stripped manifest resolves `subx-core` from the registry.

**4. Release-pending prose is retired into release-prep prose.** The user-facing `[2.0.0]` section of `CHANGELOG.md` is rewritten per the changelog convention (the current text carries proposal IDs, file:line citations, CI job internals and pending-release caveats that belong to the working record, not to release notes), the `[Unreleased]` entries fold into it, and the AGENTS.md / `docs/tech-architecture.md` / README release-publishing prose is rewritten for the per-repository topology — still honestly saying *not yet published*, because at the time of this change no tag has been cut in either repository.

## Capabilities

### Modified Capabilities

- `release-distribution`: **MODIFIES** *Two-Crate Publication Order and Preconditions* — publication moves from one shared workspace publish to one publish per repository, ordered by an index precondition probe in the consumer's job instead of by intra-job topological ordering; the Cargo ≥ 1.90 floor retires with the command that needed it; the recovery section is restated for single-upload jobs.
- `crate-topology`: **MODIFIES** *The Core Repository Has Its Own CI* — the core repository is permitted (and now required by the release contract) to carry its own `release.yml`; "publication stays single-pathed" is restated as *each crate publishes exactly once, from the repository that owns it*, which is what actually prevents a version no consumer can pin.

## Impact

- **Workflows:** new `subx-core/.github/workflows/release.yml`; `.github/workflows/release.yml`'s `publish-crates` rebuilt from six publish steps to five, single-crate. `create-release`, the five-target `build` matrix, and the `build-test-audit-coverage.yml` files are untouched.
- **Specs:** the two requirements named above. No capability is created or removed.
- **Docs:** `AGENTS.md` and `subx-core/AGENTS.md` release prose (outside the `SHARED_CONVENTIONS` region in both); `docs/tech-architecture.md` CI/CD + Distribution sections; `CHANGELOG.md` `[2.0.0]` rewrite with `[Unreleased]` folded in; `subx-core/CHANGELOG.md` `[1.0.0]` rewritten for library consumers; all four READMEs gain the crates.io/docs.rs badge rows and corrected library-consumption prose.
- **Code:** none. No `.rs` file, no manifest, no lockfile changes.
- **Secrets:** none added — `CARGO_REGISTRY_TOKEN` already exists in both repositories' Actions configuration; the core workflow uses its own repository's copy.
